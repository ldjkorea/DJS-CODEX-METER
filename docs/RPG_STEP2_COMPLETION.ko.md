- 요청한 모델/추론강도 설정을 이 작업에서 변경·검증하지 않았다.

## 2. 대한민국·세계 모델

모델 ID는 `rpg-2026q2-v1`, 게임 점수는 0~100이다. 실제 국가 순위·백분위가 아니다.

주 자료는 [Microsoft AI Diffusion Q2 2026 발표](https://news.microsoft.com/source/asia/2026/09/28/마이크로소프트-2026년-2분기-글로벌-ai-확산-보고서-발표/?lang=ko)다.
2026-09-28 발표, 관측 기간 2026년 2분기, 모집단 15~64세 생산연령인구. 비식별 텔레메트리를 시장 점유율·인터넷 보급률·인구 등에 맞춰 보정한 지표다. 한국 40.6%, 세계 18.8%를 확인했다.
이는 개인 토큰 분포가 아니므로 실제 상위 몇 %라는 표현에 사용하지 않는다.

사용 빈도는 [Gallup Q4 2025 보고서](https://www.gallup.com/workplace/701195/frequent-workplace-continued-rise.aspx)를 추가 검토했다. 2026-01-25 발표, **미국 근로자** 대상 일일 12%, 주 수회 이상 26%다. 한국·세계 전체 빈도로 일반화하거나 토큰 분포에 대입하지 않고, 일일 활동을 높은 지속성으로 취급하는 참고 자료로만 사용했다.

최종 점수:

`0.40 × 활동·지속성 + 0.35 × 토큰 강도 + 0.25 × 한도 활용도`

- 활동·지속성: 최근 30일 활동일 비율 75점 + 최근 8주 유효 주간 비율 25점.
- 활동 목표일은 `12 + round(30 × AI 이용률)`이라는 **게임 가정**으로 한국 24일, 세계 18일이다.
- 토큰 강도는 `100 × min(1, ln(1 + 최근30일 토큰/100만) / ln(1 + 기준/100만))`이다.
- 월 토큰 기준은 한국 30억, 세계 20억이라는 **게임 가정**이다. 공개 조사에서 이 개인 분포를 관측했다고 주장하지 않는다.
- 한도 활용도는 1단계 실제 결제 기간 결산이다. 금액은 점수에 사용하지 않는다. 결제 등록이 없으면 최근 4~8개의 인증된 주간 **정규화 점수의 평균**을 별도 근거로 사용할 수 있다. 월간 가성비로 표시하지 않는다.
- 없는 입력은 0으로 만들지 않고 가중치를 재정규화한다. 토큰/비교 구간이 부족하면 잠정 배치로 제한한다. 유효 4주와 비교 입력을 확보하기 전에는 신규 배치가 PLATINUM을 넘지 않는다.
- 동일 자료에 두 모델을 적용한다. 세계를 한국보다 항상 한 단계 높이는 코드가 없다. 충분히 높은 활동에서는 두 결과가 같을 수 있다.
- 일별 토큰의 서비스 날짜와 서울 관측 날짜는 따로 유지한다. 시간대가 불명확한 두 날짜 집합을 합치지 않고 활동일 수의 최댓값을 보수적 하한으로 사용한다.

## 4. 토큰 실제 확인 결과

공식 [Codex App Server 문서](https://learn.chatgpt.com/docs/app-server)의 `account/usage/read`와 실제 설치 CLI `0.156.1`의 생성 스키마를 확인했다.
읽기 전용 별도 App Server에서 실제 로그인된 계정의 해당 RPC를 실행했다. 추론 턴을 시작하거나 Codex 설정을 변경하지 않았다.

- 공식 `summary.lifetimeTokens`: **2,733,583,253**.
- `peakDailyTokens`: **735,977,532**.
- 마지막 30개 서비스 날짜 버킷 합: **2,515,535,439**, 30일당 평균 약 **8,385만**.
- 마지막 7개 버킷 평균 약 **2.66억/일**. 최근 집중 사용 속도이며 장기 일정 속도라고 가정하지 않는다.
- 이 요약은 백엔드의 토큰 활동 지표다. 입력+출력 원시 합, 결제 토큰 또는 계정 한도 차감으로 바꾸지 않는다.
- 요약의 일별 날짜 시간대는 미확인 상태로 남겼다.

로컬 최근 24개 세션에서 `token_count` 10,460건을 확인했고 `token_usage_record`는 이 조사 범위에서 없었다.
실제 필드는 `input_tokens`, `cached_input_tokens`, `cache_write_input_tokens`, `output_tokens`, `reasoning_output_tokens`, `total_tokens`였다.
24개 중 23개의 `creator_account_id`가 현재 안전한 계정 식별과 일치했다. 부모/상속 기록은 중복 가능성 때문에 로컬 보완 합계에서 제외한다.

실제 완성된 C# 수집기로도 동일한 공식 누적값 조회가 성공했다. 계정 귀속과 부모/상속 제외 조건을 통과한 루트 세션 6개의 토큰 메타데이터를 확보했다. 이 검사에서 실행 중인 Windows 위젯이나 휴대폰 DB에 결과를 쓰지는 않았다.

Windows 수집기는 시간당 최대 한 번 공식 요약을 읽는다. 기존 15초 작업 상태 폴링 빈도와 OAuth/API 형식은 유지한다.
공식 값을 기준으로 삼고, 계정 확인된 루트 세션 최대 24개의 최근 2MiB에서 토큰 메타데이터만 보완한다.
공식 누적값과 로컬 누적값을 더하지 않는다. 동일 세션 누적은 최댓값으로 교체한다. `last_token_usage`는 최신 모델 응답이며 전체 턴 토큰 합이라고 표시하지 않는다.
캐시 입력은 입력의 일부, 추론 출력은 출력의 일부다. 별도로 더해 총 토큰을 늘리지 않는다.
로컬 누적 카운터만으로 날짜별 소비나 토큰 일일 XP를 만들어내지 않는다. 상속 이력이 있거나 계정 귀속이 불명확한 로그는 제외한다.
프로젝트 대화·프롬프트·코드·비밀키·인증 토큰은 RPG 저장 및 전달 자료에 넣지 않는다.
토큰 저장 실패는 기존 작업 상태 및 사용량 동기화 성공을 막지 않도록 선택 기능으로 격리했다.

## 5. XP와 과거 이관

`profiles(account SHA-256, document)`의 기존 SQLite 스키마를 유지한다. `document.future.rpg`에 버전, 지급 대상, 활동일, 인증 주간, 토큰 메타데이터, 업적, 칭호, 지역별 티어를 저장한다.
1단계 결산/인증정보를 변경하지 않는다. 최초 쓰기 전에 기존 RPG DB와 WAL/SHM을 `files/rpg-step2-recovery`에 복사한다. 기존 1단계 복구 사본도 유지한다.

| 보상 | 규칙 |
|---|---|
| 활동일 | 확인된 계정 활동일당 20 XP. 서울 기록/서비스 날짜 범위의 최댓값을 사용하여 중복 지급 방지 |
| 토큰 일일 | `min(75, floor(15 × log10(1 + 토큰/1000)))` |
| 한도 소비 | 날짜별 `min(25, floor(25 × ln(1+%p)/ln(101)))`. 서로 다른 한도의 보상을 합산하지 않고 가장 큰 확인 보상 대상 사용 |
| 인증 주간 | 계정·구간 종료 시각당 50 XP |
| 업적 | 고유 ID별 최초 달성 시에만 고정 보상 |

XP는 지급 항목별 누적 목표의 증가분만 더한다. 원장을 다시 읽거나 기기 사본을 병합해도 XP 총합을 더하지 않는다.
서버 보정·초기화·플랜 변경·칭호 선택으로 기존 XP를 감소시키지 않는다.

레벨 L의 필요 누적 XP: `50 × L × (L−1)`.
레벨: `1 + floor((sqrt(1 + 8×XP/100)−1)/2)`.
Lv.100에서 종료하지 않고 Lv.150 이후도 테스트했다.

| 일일 기본 XP 가정 + 주간 50 XP | 1년 | 3년 | 10년 |
|---|---:|---:|---:|
| 35 XP | Lv.18 | Lv.30 | Lv.55 |
| 80 XP | Lv.25 | Lv.44 | Lv.80 |
| 120 XP | Lv.30 | Lv.53 | Lv.96 |

이 표는 활동을 매일 지속한다는 가정이며 업적 보너스를 제외한 시뮬레이션이다.

소급 대상은 정상 증가가 확인된 일별 기록, 인증된 과거 주간 결산, 보존된 최고 티어, 실제 토큰 자료다.
이미 원시 기록이 정리된 주간도 옛 결산의 인증 품질·관측 수·7일 구간을 검사해 주간 XP를 복구한다. 전체 주간 합계로 일별 활동이나 연속 출석을 지어내지 않는다.
같은 계정의 Pro→Free→Pro 변경에는 계정 문서가 유지된다. 결제 가격과 현재 한도는 기존 플랜별 저장을 따른다.
삭제 경계 이전 raw 자료의 재이관은 막고, 이미 획득한 계정 성취는 유지한다.
계정이 다른 토큰/복구 문서는 거부한다. 복구는 사본에서 검증한 후 SQLite 트랜잭션으로 저장한다.

복구 인터페이스는 기존 인증된 계정에서만 사용할 수 있다. 임의 XP 키를 거부하며, 활동/토큰/한도 기록을 병합하고 지급 항목의 최댓값만 반영한다.
**재설치 이후 복구 UI와 기기 간 전체 RPG 문서 자동 전달은 3단계 연결 대상이다. 이번에는 엔진/저장 인터페이스와 반복 병합 검증까지 구현했다.**

## 6. 업적·칭호

41개 업적과 각 업적에 연결된 41개 독립 칭호를 한국어·영어로 정의했다.
토큰 7개, 누적 활동일 7개, 연속 활동 4개, 장기 주간 5개, 티어 10개, 특별/복합 8개다.
고유 ID, 이름, 조건, 진행률, 희귀도, 최초 검증 해금 시각, 데이터 근거, 지급 XP와 해금 여부를 저장한다.
복구된 업적의 정확한 과거 달성 시각을 모르면 최초 확인 시각으로 명시한다.

토큰 단계: 100만 / 1,000만 / 1억 / 10억 / 100억 / 1,000억 / 1조.
상위 100억에는 활동 365일+인증 26주, 1,000억에는 활동 730일+인증 52주, 1조에는 활동 1,825일+인증 156주를 추가한다.
최근 확인한 30일 평균 속도가 지속된다면 각각 약 119일/3.3년/32.7년이지만, 100억은 365일 활동 조건 때문에 그보다 일찍 열리지 않는다. 최근 7일 급증 속도는 장기 기준으로 사용하지 않았다. 상위 값은 v1 게임 목표이며 달성 기간 보장이 아니다.

칭호 추천은 적격 후보 안에서만 선택하고 저장한다. 화면 읽기/일반 갱신으로 다시 뽑지 않는다.
사용자는 해금한 칭호만 장착할 수 있다. 장착은 XP·티어에 영향을 주지 않는다.
전체 조건과 칭호는 [업적 도감](RPG_STEP2_ACHIEVEMENTS.ko.md)에 정리했다.

초기 검증에서 발견하고 수정한 문제:

- 지역 티어 승급 다음 조회 때 업적이 뒤늦게 해금되던 순서를 수정하여 반복 가져오기 XP 증가를 막았다.

- 표시 캐시가 사라진 뒤 복구 결과를 캐시에 재저장하지 않던 경로를 수정했다. DB 복구와 캐시 재생성을 기존 동기화 잠금 안에서 수행하여 오래된 조회가 새 저장 결과를 덮어쓰지 않도록 했다. 수정 전 최종 에뮬레이터 반복 조회 시간 검사가 실패했고, 수정 후 같은 조건을 통과했다.
- 누적 토큰만 있고 일별 자료가 없으면 강도를 0으로 대입하지 않고 미확인 입력으로 제외한다. 복구 시 지역 티어의 인증 주간 점수와 평가 이력도 승계한다.

성능:

## 8. 3단계 연결 인터페이스와 남은 경계

| 인터페이스 | 용도 |
|---|---|
| `RpgProgressStore.progress(context)` | 현재 계정의 작은 레벨/XP/지역 티어/토큰 상태/칭호 요약 |
| `RpgProgressStore.tokens(context, expectedAccount, envelope)` | 인증된 LAN/Tailscale에서 받은 공식 메타데이터 저장 |
| `RpgProgressStore.equip(context, expectedAccount, titleId)` | 적격 칭호 장착 및 영구 보존 |
| `RpgProgressStore.export / restore` | 계정 바인딩된 RPG 사본과 멱등 병합. 3단계에서 백업/기존 인증된 동기화 UI 연결 |
| `RpgEngine.eligibleTitles / recommend` | 해금 목록과 명시적 재추천. 화면 조회는 재추천하지 않음 |
| `RpgCatalog.ALL` | 41개 업적/칭호/영문/조건/희귀도/보상 정의 |
| `RpgEngine.evaluateCertifiedWindow` | 실제 시간대·전체 범위가 확인된 자료가 있을 때만 지역별 보호 강등 평가 |

UI에서는 `label=game_estimate`, `provisional`, `token_status`, `token_observed_at`, `token_basis`, `daily_basis`, `quota_score_basis`, `demotion_status`를 읽는다.
공식 계정 요약 토큰과 로컬 입력/캐시/출력은 서로 다른 포함 범위로 보여야 한다. token total을 한도 % 또는 API 비용으로 바꾸지 않는다.
전체 RPG 자동 기기 공유/재설치 복구 화면, 새 도감·레벨·지역 티어 화면은 3단계 범위다.
공식 토큰 날짜의 시간대·완전한 범위를 확정하기 전에는 새 지역 티어의 자동 강등을 보류한다.
추가 AI 호출·참여자 수집 서버·새 SDK를 추가하지 않았다. 3단계를 자동 시작하지 않는다.
