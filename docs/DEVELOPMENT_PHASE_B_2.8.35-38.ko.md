## 2. 내부 35 — 원장·정밀도·시계 오차

### 확인된 결함과 수정

1. `LiveUsageStore`의 갱신 식별값과 SQLite 실패 시 호환 저장 경로가 정수 사용률을 사용했다. 정수 부분이 같은 소수값 변화를 놓치거나 정밀도가 손실될 수 있었다. 원본 `preciseUsedPercent()`를 사용하도록 수정했다. 서버가 정수만 반환하면 추가 소수값을 만들어내지 않는다.
2. `LedgerCapture`가 같은 구간에 정수 반올림값이 같은 후보를 잘못 매칭할 수 있었다. 정확한 소수값 일치를 우선하며, 옛 정수 스냅샷에서 원본 응답의 정밀도를 복구할 때는 후보가 하나로 확인되는 경우만 허용한다. 모호한 후보를 임의로 선택하지 않는다.
3. 기존 LAN 수신은 PC 시계 오차를 최대 5분까지 허용하지만, 수신한 미래 관측을 당일 소비량에 즉시 반영했다. 원본 관측은 유지하고 `rollup()`에서 현재 시각 이후 관측을 집계에서 제외한다.
4. 미래 관측이 해당 한도의 최신 시각이 되어 휴대폰의 현재 정상 저장을 거절했다. 역순 검사에서 현재 시각까지의 관측만 비교한다. 과거 응답 차단을 유지하면서 미래 PC 기록이 정상 휴대폰 관측을 막지 않도록 수정했다.

미래 증거가 실제 현재 시각에 도달한 후에는 기존 유지보수·재집계 경로에서 평가할 수 있다. 기록 시각을 임의로 현재 시각으로 바꾸지 않는다.

### 유지한 계산·저장 정책

- `LedgerAggregation`, `MonthlyLedger`의 산식, DB 스키마/버전과 계정 범위를 변경하지 않았다.
- 동일 한도·정책·초기화 구간의 확인된 증가량만 소비로 사용한다. 정상 5시간/주간 초기화, 조기 구간 변경, 확인된 크레딧 이벤트, 보정, 정책 변경, 공백을 기존 규칙으로 구분한다.
- 외부 발표를 근거로 전역 리셋 원인을 확정하지 않는다. 서버와 기록만으로 원인을 입증할 수 없으면 미확인 변화로 남긴다. 전역/조기 리셋 모양의 합성 자료 검증은 실제 원인 판정과 다르다.
- 자정·결제 경계·공백을 가로지르는 미확인 소비를 날짜에 임의 배분하지 않는다. 0 사용과 자료 부족을 구분한다.
- 원시 기록 90일, 일별 집계 750일의 기존 보존 정책과 경계 관측 보존을 유지한다. 오래된 원시 기록을 다시 가져와 확정 보관 집계를 덮어쓰지 않는다.
- 관측 식별자 `meter + observed_at`, 삭제 워터마크, 이관 표식을 유지한다. 동일 자료 재수신, 재시작, 반복 이관에서 중복을 방지한다.
- 실제 SQLite로 중복·역순·시계 오차·재시작·삭제 후 재유입 차단·잘못된 배치 전체 롤백을 검증했다. 합성 DB이며 사용자 기록을 삭제한 검증이 아니다.

## 3. 내부 36 — 독립 수집·XP·티어

### 칭호 OFF 기간 메달 유입 수정

`TitleJourney`의 복합 칭호 조건은 메달 획득일이 칭호 최초 시작일 이후인지 확인했지만, **칭호 OFF 기간에 얻은 메달**도 재개 후 조건에 포함했다.

칭호 저널에 선택적 `linked_medals` 근거를 추가했다. 현재 ON 구간에서 실제 획득한 메달 ID·최초 획득 시각만 등록하고, 이전 ON 구간의 근거는 재개 후에도 유지한다. 메달 ID와 시각을 검사하며 동일 도전의 복원에서 멱등 병합한다. 이미 획득한 칭호·메달·XP를 제거하거나 다시 지급하지 않는다.

옛 저널에는 이 근거가 없다. 기존 해금 상태는 보존하며 현재 연속 ON 구간에서 입증 가능한 자료를 사용한다. **이미 닫힌 옛 ON/OFF 구간의 누락된 근거는 추정하지 않으므로 일부 새 복합 칭호의 추가 해금은 보류될 수 있다.** 과거 메달 자체나 진행률을 초기화하는 정책은 아니다.

| 업적 | 칭호 | 검증한 수집 동작 |
|---|---|---|
| OFF | OFF | 새 수집 해금 없음. 기존 XP·레벨·보관함 유지 |
| ON | OFF | 시작 후 업적만 진행. 칭호 OFF 기간 메달은 이후 새 복합 칭호 근거에서 제외 |
| OFF | ON | 칭호의 독립 활동 조건은 진행. 새 메달을 요구하는 조건은 근거가 없으면 보류 |
| ON | ON | 각 시작 시점 이후 조건을 독립 평가. 실제 ON 중 획득 메달만 연계 |

처음 ON 이전 활동, OFF 기간 활동의 소급 제외, 재개 진행 유지, 계정 분리, 요금제 변경, 반복 복원, 잘못된 미래 근거의 원자적 거부를 검증했다. 기존 53개 업적 ID·조건·칭호 ID·장착값·대표 메달 정책을 변경하지 않았다.

### 운영 티어 평가 경로

현재 소스에는 이미 다음 운영 연결이 존재했다. 불필요한 새 호출을 추가하지 않았다.

`RpgProgressStore → RpgEngine.reconcile/ingestOfficial → evaluateAvailableWindows → evaluateCertifiedWindow → RpgTier.week`

실제 `RpgProgressStore`와 SQLite에 합성 계정·명시적으로 인증된 Asia/Seoul 계정 전체 주간 자료를 넣어 갱신 경로를 실행했다. 비교 가능한 충분한 주간 및 장기 점수 조건에서 대한민국·세계 각각 1단계 강등, 최고 기록 유지, 같은 입력 재처리 시 추가 강등 없음, 조회 실패 시 보류를 확인했다.

기존 회귀 검사에서 정상/조기 리셋, 관측 공백, 1~2주 저활용, 장기 점수 부족, 승급 2주 보호, 최고 등급 보존, 계정·시간 범위, 대한민국·세계 독립 평가를 확인했다. 신규 XP·티어 공식 변경은 없다.

**실제 수집 범위 제한:** 현재 Windows `RpgTokenReader.Project`는 서비스 일별 토큰의 계정 전체 범위·달력 시간대를 인증하지 않는다. 해당 증거가 없으면 운영 평가가 안전하게 강등을 보류한다. 합성 인증 계약 검증은 실제 사용자 계정의 완전한 주간 자료 확보를 의미하지 않는다. 이 보류를 임의의 완전한 주간 생성으로 해제하지 않았다.

## 4. 내부 37 — 작업 상태의 근거·역순·위젯

- `TaskStatusData`에서 한 프레임의 중복 작업 ID를 거부한다.
- 프레임 전체의 최신 작업뿐 아니라 **동일 작업별 Sequence/At**의 역행을 검사한다. 한 작업이 새로워져도 다른 작업의 오래된 상태로 덮어쓰지 못한다.
- 같은 Sequence이면 작업 상태·턴·이름·관측 경고 등 핵심 메타데이터가 같아야 한다. 저장/재로드의 JSON 정수 타입 차이는 정규화해 비교한다.
- Sequence·시각 필드의 소수값을 정수로 잘라 허용하지 않고 거부한다.
- `TaskStatusStore.save()`는 거절된 응답을 성공처럼 처리하지 않는다. 마지막 정상 스냅샷·수신 시각을 유지하고 호출자에게 실패를 전달한다.
- LAN 이력 갱신 경로의 작업 수신 실패도 연결 실패 표식을 남긴다. 실제 표시가 즉시 회색 상태로 전환하며 오래된 작업을 현재 실행 중으로 오인하지 않는다. 정상 재수신에서 복구된다.
- 위젯의 큰 글꼴 열 전환과 최대 표시 개수를 공통 `widgetCapacity()`로 맞췄다. 좁은 화면·큰 글꼴에서는 가독성을 위해 1열과 적은 표시 개수를 사용한다.
- 기존 최대 6개 작업, 5×3 기본 크기, 상세 진입, 새로고침, 마지막 연결 표시를 유지한다. 사용량 위젯·삼족오·RPG UI를 새로 디자인하지 않았다.

확인된 시작은 녹색 진행 중, 턴 완료/중단은 빨간색 문구, 연결 실패/오래됨/미확인은 회색이다. 개별 도구 오류를 전체 작업 실패로 확대하지 않는다. 신뢰 가능한 이벤트가 없는 승인·입력 대기, 완료율, 예상 시간을 만들지 않는다. 턴 완료는 프로젝트 전체 완료를 뜻하지 않는다.

이 PC의 `.codex/sessions`를 읽기 전용 관측기로 확인했을 때 신선한 작업 2개·진행 중 2개·제목 있는 작업 2개가 관측됐다. 별도 제한된 최근 로그 메타데이터 조사에서도 시작/턴 완료 이벤트를 확인했다. 기존 프로그램·현재 Codex 세션을 종료하거나 로그를 수정하지 않았다. 이번 실제 표본의 중단·오류 사례는 없었으며 해당 상태는 합성 로그로 검증했다.

## 5. 내부 38 — LAN/Tailscale 수신·재시도

### Windows 수정

- 프로토콜 버전·발급 시각·삭제 기준·결제 경계 등 정수 필드를 엄격히 검사한다. `PhoneMirror.Issued`로 관측 시각이 같아도 발급 시각이 역행한 오래된 요청을 차단한다. 이전 미러에는 선택적 기본값 0을 적용한다.
- 관측 원문 소수 문자열과 수치의 일치를 검사한다. 없던 옛 문자열은 실제 저장 수치로만 보완한다.
- 공유 이력을 임의 요청 전체 복사 대신 검증된 필드 목록으로 구성한다. 일별/이벤트의 타입·길이·범위·정책·날짜를 검증하며 알려지지 않은 중첩 필드는 저장/전송에서 제외한다.
- 계정별 `push-nonces.json`에 요청 ID·발급 시각·정규화된 SHA-256만 기록한다. 재시작 후에도 동일 ID로 내용을 바꾼 재생을 거부한다. 정확히 같은 재시도는 멱등 처리하며 OAuth·페어링 비밀·원본 요청은 이 저널에 저장하지 않는다.
- 유효 요청의 기존 5분 범위 안에서 저널을 정리하고 최대 2,048개로 제한한다. 손상된 저널은 인증을 우회하거나 삭제해 복구하지 않고 실패로 처리한다.
- Windows 일별 사용량도 미래 관측을 조기 소비로 합산하지 않는다.

기존 프로토콜 v1, 계정 해시, 페어링 비밀, TLS 인증서 고정, LAN/Tailscale 허용 범위, PC 제목 개인정보 필터, 전송 6개 상한을 보존했다. 리스너·포트를 외부에 새로 공개하지 않았다.

Windows 파일 저장은 **파일별 원자적 교체와 멱등 재시도**이며 여러 날짜 파일 전체를 묶는 단일 트랜잭션은 아니다. 중간 장애 후 동일 요청 재시도로 진행할 수 있지만 전체 배치의 동시 원자성을 주장하지 않는다. Android 원장 배치는 SQLite 트랜잭션으로 검증했다.

### 연결 검증 범위

- 실제 Java Android 통신 구현과 C# 서버를 격리된 로컬 TLS 연결로 실행했다. 정상 왕복, 잘못된 인증서·비밀·계정 거절, 실패 뒤 정상 연결 복구를 검증했다.
- Windows 합성 서버 재시작에서 페어링 비밀·인증서 고정·보호된 토큰 파일의 바이트를 보존했다.
- Wi-Fi/VPN/모바일 전환 의사결정, 사설 주소·Tailscale 범위, 오래된 응답, 중복 메타데이터는 대상 테스트로 검증했다.

## 9. Phase C 인수인계 위험

1. 실제 일별 토큰의 계정 전체 범위·시간대 인증이 부족하면 강등이 보류된다. 완전한 주간을 가정하거나 로컬 토큰과 공식 요약을 합산해 우회하지 말 것.
2. 옛 칭호 저널의 이미 닫힌 ON 구간은 메달 연계 근거가 부족할 수 있다. 기존 성취는 유지하되 추가 근거를 추정해 만들지 말 것.
3. PC/폰 시계 오차와 실제 LTE/Tailscale, 절전·Doze·백그라운드 복귀는 실기기로 확인해야 한다. 미래 기록 보류는 두 기기의 정확한 시계 동기화를 대신하지 않는다.
4. Windows 저장은 다중 파일 단일 트랜잭션이 아니다. 손상된 재생 저널은 실패로 닫히며 자동 삭제/인증 완화로 해결하면 안 된다.
5. 이번 UI 증거는 기존 에뮬레이터·격리 계정의 실제 렌더다. 삼성 런처 크기, 설치 업데이트 후 실제 기록 보존, 로그인·실제 API, Wear/AOD/Now Bar는 추가 실기기 검증이 필요하다.
6. 내부 작업은 기존 공개 버전 2.8.30을 유지했다. 후속 기능의 통합·검증 및 별도 배포 지시 없이 공개 Tag/Release를 만들거나 중간 버전을 배포하지 말 것.

**판정:** Phase B 구현·로컬 검증 완료. 실제 PC의 읽기 전용 상태 관측과 에뮬레이터 렌더를 확인했다. 실제 사용자 휴대폰 연결·사용자 데이터 복구·정식 배포 완료 상태는 아니다.
